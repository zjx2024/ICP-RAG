# ICP-RAG 开源本地化完整实施方案

本文档给出 ICP-RAG 在单机或局域网环境中的完整技术方案、数据分层、检索流程、迁移与验收标准。它是实施基线，不改变产品边界：用户侧仍然只有七类工程文档、一个统一上传入口、ICP 故障诊断和系统设置；不恢复独立图片画廊，也不破坏 Dify 兼容接口。

## 1. 已确认的技术栈

| 职责 | 选型 | 本项目中的定位 |
|---|---|---|
| 权威关系数据 | PostgreSQL 15 | 文档登记、解析状态、结构化事实、模型配置和来源引用的唯一权威来源 |
| 全文与向量检索 | OpenSearch | 同一版本化索引内提供 CJK BM25、精确过滤和 BGE-M3 1024 维 k-NN 召回 |
| 原件与证据文件 | ArtifactStore + LocalFS | 保存原始 Word/Excel、抽取图片和解析产物；业务代码只依赖 storage key |
| 图关系投影 | HugeGraph | 保存通过自动校验且适合多跳查询的关系投影，以及仅供浏览的 `provisional` 投影；不承担唯一事实来源 |
| LLM 服务 | Ollama + Qwen3.6 | 本地完成意图理解、工具规划、证据解释、追问和答案组织 |
| Embedding | BGE-M3 | 通过 Ollama `/api/embed` 批量生成固定 1024 维向量 |
| Rerank | BGE-Reranker-v2-M3 | 对融合去重后的全部候选重排序，再截取最终 `top_k` |

所有运行数据和模型均应能在内网自部署。镜像、模型权重及其许可证必须在交付时形成版本清单；具体许可证以实际下载的镜像、源码和模型卡随附文件为准。

### 1.1 为什么不使用 Milvus

本方案不部署 Milvus，也不保留它作为隐藏的第二套向量写入目标。原因是：

- OpenSearch 已同时满足中文全文、业务字段精确过滤和 1024 维向量召回；
- BM25 和向量候选共享 `doc_id`、业务 ID、版本/构型标签及同一索引生命周期，过滤语义更一致；
- 减少一套数据复制、失败补偿、备份、监控、容量规划和权限体系；
- PostgreSQL 与原始文件可以重建 OpenSearch，系统仍保持清晰的单向投影关系。

只有在真实评测证明 OpenSearch 无法达到既定容量、延迟或召回目标，并且收益足以覆盖双写一致性成本时，才重新评估独立向量库。在此之前，不增加 Milvus 容器、端口、卷、SDK 或配置项。

## 2. 总体分层与数据所有权

```text
统一上传入口
   │
   ├─ ArtifactStore + LocalFS ── 原件、图片、解析产物、可复核证据
   │              │
   │              └─ storage_key / source_ref
   ▼
PostgreSQL 15 ─────────────── 权威文档状态与七类结构化事实
   │
   ├─ 可重建投影 ──► OpenSearch ── CJK BM25 + BGE-M3 k-NN + 精确过滤
   │
   └─ 自动校验投影 ─► HugeGraph  ── 正式多跳关系与 provisional 浏览图
                         │
                         ▼
Ollama/Qwen3.6 + 领域工具 + BGE-Reranker-v2-M3
                         │
                         ▼
候选诊断、依据、来源、待确认项和区分性追问
```

四类存储不是“三选二”：

- 七类文档的原件都进入 ArtifactStore；
- 七类文档的登记、状态和可验证结构化结果都进入 PostgreSQL；
- 七类文档中需要被检索的记录都生成 OpenSearch 文本/向量投影；
- 七类文档都可以贡献图关系，但只投影具有明确业务 ID、明确来源且适合多跳查询的关系。普通段落和每个向量片段不应被强制转换成图节点。

数据优先级固定为：

```text
正式回答详情：PostgreSQL
原文与工程图证据：ArtifactStore
候选召回：OpenSearch
关系扩展：HugeGraph
```

当不同存储内容冲突时，以 PostgreSQL 及其 `source_ref` 指向的原始证据为准；OpenSearch 和 HugeGraph 必须重建或修复，不能反向覆盖权威事实。

## 3. 统一标识和来源链

所有跨存储记录至少携带：

| 字段 | 作用 |
|---|---|
| `doc_id` | 一份上传文档的稳定 ID，关联 `icp_documents` |
| `doc_type` / `doc_type_kwd` | 严格限制为七类文档之一 |
| 业务 ID | 如 `function_id`、HMC 码、FMECA 代码、MFL 代码、案例 ID、图节点 ID |
| PostgreSQL ID | OpenSearch 中使用 `pg_id_kwd` 回查权威行 |
| `source_ref` | 页码、表格/行、章节、图片或原件 storage key 等来源定位 |
| `image_url` / image storage key | 需要时关联工程图证据，不提供全局画廊 |
| 文档元数据 | 系统、构型、版本、数据状态等适用范围 |

OpenSearch `_id` 应由 `doc_id + 业务行 ID + 投影用途` 确定性生成，使重复解析和重建保持幂等。HugeGraph 顶点和边也必须使用确定性业务键，且保存 `doc_id`、业务 ID、`source_ref` 和 `validation_status`。

## 4. 七类文档的处理与存储映射

### 4.1 总体映射

| `doc_type` | ArtifactStore + LocalFS | PostgreSQL 权威事实 | OpenSearch 检索投影 | HugeGraph 关系投影 |
|---|---|---|---|---|
| `function_locator` | 原始文档、架构图、抽取图片 | `icp_documents`、`icp_functions`、相关图片/表格引用 | 系统、子系统、模块、功能、接口、描述、别名、典型失效表现；一条功能记录或可追溯片段一个投影 | `系统→子系统→模块→功能→接口/输入输出`，功能与失效表现的明确关系 |
| `hmc` | 原始 Word/Excel、相关表格证据 | `fault_hmc`；LCN/HAMC/HSC 始终按字符串保存 | 每条记录生成“诊断”和“维修”两个用途不同的投影，保留 HMC/LCN/HAMC/HSC 精确字段 | HMC 与模块、功能、故障现象、维修动作之间的明确关系；无明确实体时不强造边 |
| `fmeca` | 原始文档和宽表证据 | `fmea`；每个故障模式独立记录 | 产品/功能、故障模式、原因、阶段、影响、严酷度、概率、检测及补偿措施的行级投影 | `产品/功能→故障模式→原因/影响/检测方法`，仅使用表内明确关系 |
| `mfl` | 原始文档和表格证据 | `mfl`；布尔值规范化并保留来源 | MFL 代码、模块/SUR/子电路故障、API、调用方式和实验状态的行级投影 | `模块/SUR/子电路故障→API→维修定位`，以及显式 HMC/FMECA 关联 |
| `fta` | 原件、故障树原图和视觉解析中间产物 | `document_fault_trees` 中的节点、边、逻辑门、参数、来源和版本化自动校验状态 | 顶事件、事件说明、节点、逻辑门和分析段落；图片文本也保留来源 | `auto_validated` 投影可支持正式拓扑；`provisional` 仅供浏览；`quarantined` 不入推理图 |
| `rbd` | 原件、可靠性框图和视觉解析中间产物 | `document_fault_trees` 中按 RBD 语义保存的块、路径、参数、来源和版本化自动校验状态 | 功能块、串并联/冗余结构、成功判据、可靠度参数和说明 | `auto_validated` 投影可支持正式拓扑；`provisional` 仅供浏览；`quarantined` 不入推理图，且不得套用 FTA 语义 |
| `fault_history` | 原始文档、案例图片和附件 | `fault_history_cases`、`fault_history_steps` | 现象、设备、模块、排故方法、根因、步骤、方案、预防措施和交叉引用的案例级投影 | `案例→现象/模块/根因/步骤/方案` 以及明确的 HMC/FMECA/FTA/MFL 关联 |

### 4.2 HMC 的双投影

HMC 必须区分两种检索意图：

```text
诊断投影：HMC + LCN/HAMC/HSC + 故障现象
维修投影：HMC + 故障现象 + 故障分析程序/维修方法
```

这样既能从现象找到候选故障，又避免大量重复的维修动作淹没诊断语义。完整 HMC 或完整 `LCN + HAMC + HSC` 输入始终先精确查 PostgreSQL，OpenSearch 只用于模糊补充召回。

### 4.3 FTA 与 RBD 的自动校验和投影边界

FTA、RBD 和架构图解析后进入版本化自动校验，不以人工确认作为日常入图前置条件：

1. 来自确定性表格或受控表达式、且节点类型、边方向、逻辑门/串并联语义、参数单位和适用范围均通过约束的修订标记为 `auto_validated`；
2. 仅来自视觉模型、结构完整且达到置信阈值的修订标记为 `provisional`，可投影用于浏览和定位原图，但不得支持正式拓扑结论、唯一诊断或可靠性数值计算；
3. 存在冲突、残缺、悬空边、非法参数、低置信或抽取歧义的修订标记为 `quarantined`，不得进入推理图；
4. `manual_confirmed` 只兼容历史上已经显式确认的修订，不是新解析流程的必要状态，也不要求用户逐图审核；
5. 所有状态都必须保留原图和 `source_ref`，且只能由确定性校验器推进，LLM 不得直接修改验证状态。

FTA 最小割集、顶事件概率和 RBD 可靠度必须由确定性 Python 代码计算。正式计算只接受当前有效、已发布的 `auto_validated` 修订，或兼容保留的 `manual_confirmed` 修订；LLM 只解释输入、缺失参数和结果，不生成数值。

## 5. 文档通用元数据与标签

### 5.1 字段集合

解析文档封面或首页表格时提取以下受控字段：

| 原始名称 | PostgreSQL JSON 字段 | OpenSearch 精确过滤字段 |
|---|---|---|
| 文档编号 | `document_number` | `document_number_kwd` |
| 适用系统 | `applicable_system` | `applicable_system_kwd` |
| 适用构型 | `applicable_configuration` | `applicable_configuration_kwd` |
| 文档版本 | `document_version` | `document_version_kwd` |
| 数据来源 | `data_source` | `data_source_kwd` |
| 数据状态 | `data_status` | `data_status_kwd` |
| 编制日期 | `compiled_date` | `compiled_date_kwd` |

这些标签有明确价值：它们能防止不同系统、构型或版本的相似片段在检索时互相污染，并能让答案明确说明适用范围。

### 5.2 存储原则

- 权威值保存在 `icp_documents.metadata` JSONB；文档详情、审计和重建都从这里读取；
- 每个 OpenSearch 投影冗余相同的 `document_metadata` 对象及 `*_kwd` 字段，用于检索前的精确过滤；
- 标签不替代正文向量，不应把一长串重复封面信息拼进每个片段后主导语义相似度；
- HugeGraph 可把适用系统、构型和版本作为顶点/边属性，但不再创建一套独立权威标签；
- 当前首版只清理多余空白并保留原值。后续如需别名、构型编码或日期规范化，新增独立规范化字段，不能覆盖原始值；
- 缺失、冲突或无法识别的标签必须显式记录，不能猜测。

### 5.3 过滤策略

用户明确给出系统、构型或版本时，先形成 OpenSearch `term/terms` 过滤，再执行 BM25 与 k-NN。用户未给出时可以召回多个适用范围，但最终回答必须：

- 显示每条证据的文档编号、版本和适用构型；
- 对适用范围冲突的候选降级或分组；
- 关键信息不足时追问当前构型/软件版本；
- 不把不同版本的数值参数混合计算。

## 6. 写入与一致性流程

### 6.1 上传和解析

```text
首页统一上传并显式选择 doc_type
→ ArtifactStore 原子写入原件
→ PostgreSQL 登记 icp_documents 和 storage key
→ 提取通用元数据并写入 icp_documents.metadata
→ ParserRegistry 路由七类专用解析器
→ PostgreSQL 写权威结构化记录与 source_ref
→ 批量调用 BGE-M3 生成 1024 维向量
→ OpenSearch 幂等 upsert 文本、向量、标签和 PG 回查键
→ 七类文档自动生成 Document 来源节点和 PostgreSQL 中明确存在的关系
→ FTA/RBD/架构图候选进入版本化自动校验
→ auto_validated 发布为正式图；provisional 仅发布浏览图；quarantined 隔离
```

该流程无需用户逐图确认；`manual_confirmed` 只兼容历史修订。业务成功的最低条件是“原件已持久化 + PostgreSQL 主记录已登记”。OpenSearch 或 HugeGraph 写入失败不能伪装成成功，也不能改用进程内临时索引；应记录失败阶段并允许从 PostgreSQL 重试/重建。

### 6.2 删除

删除顺序应能恢复和审计：

1. 标记文档删除中，阻止新解析任务；
2. 删除或失效 OpenSearch 投影和 HugeGraph 投影；
3. 删除 PostgreSQL 领域行及文档主记录；
4. ArtifactStore 将原件和证据移入 `.trash`，按保留期延迟物理清除；
5. 写删除日志，记录操作者、对象数和失败阶段。

如果中途失败，使用 `doc_id` 幂等重试；不得用模糊文件名批量删除。

### 6.3 重建原则

```text
ArtifactStore 原件 + PostgreSQL 权威事实
                ├─► OpenSearch 全文/向量投影
                └─► HugeGraph 自动校验关系投影
```

重建不得把旧检索索引中的孤儿记录当成权威数据。向量模型、维度、分块算法或 mapping 变化时必须全量重建，不能混用不同向量空间。

## 7. 查询与诊断流程

### 7.1 查询路由

请求先由 `scope_router` 判定知识库范围、能力说明、范围外问题或必要澄清；进入知识查询后，`plan` 结合当前对话对象识别本轮问题目标和必需字段，并只授权完成这些目标所需的最小工具集合：

- 完整 HMC 或 `LCN + HAMC + HSC`：PostgreSQL 精确查询优先；
- 系统架构、组成、功能、接口、输入输出：进入 Function Locator 专用流程；
- FTA/RBD 数值：仅在用户原始问题明确要求计算时，先查询可用于正式计算的结构和参数，再调用确定性计算器；
- 模糊现象：按原因、影响、维修、历史、严酷度等实际目标定向选择 Function Locator、HMC、FMECA、FTA、MFL、故障历史或混合召回；不固定扫描七类，也不强制每次先走 Function Locator；
- 明确系统/构型/版本：把它们转为精确过滤条件，贯穿所有召回和 PG 回查。

首批工具返回后，`adaptive_tools` 只检查当前目标字段是否仍有可补足缺口，并且最多再授权一批受限补查。原因分析、故障定位、架构定位或其他需要跨文档、多跳关系的问题，在获得可追溯业务实体后可自动调用 `graph_traversal`；不要求用户主动说出“关系、路径、图谱”等术语。图查询返回的每条正式关系仍须回 PostgreSQL 授权和补全来源。

### 7.2 混合检索、融合与重排

当本轮目标需要 `hybrid_search` 时，混合检索链路为：

```text
用户问题
→ BGE-M3 生成 1024 维查询向量
→ OpenSearch BM25 独立召回 top_k × 4
→ OpenSearch k-NN 独立召回 top_k × 4（带相同 metadata 过滤）
→ 加权 RRF 融合（默认 rrf_k=60）
→ 按规范化正文去重，保留 duplicate_evidence 来源
→ BGE-Reranker-v2-M3 重排全部去重候选
→ 最后截取 top_k
→ 根据 pg_id/doc_id 回查 PostgreSQL 权威详情
→ 必要时从 HugeGraph 扩展经 PostgreSQL 授权的正式关系
→ 绑定 ArtifactStore 原文/图片引用
```

BM25 分数和向量相似度不直接相加，因为两者量纲不同；RRF 使用排名融合。Rerank 分数只表示当前查询下的相关性排序，不是故障概率或工程置信度。

降级必须可见：

- Embedding 失败时保留 BM25 候选，并在检索信息中记录向量降级；
- 某一路召回失败时保留另一路，不制造空白成功；
- Rerank 未配置或调用失败时保留 RRF 顺序，并返回明确的 fallback 信息；
- PostgreSQL 回查不到主记录的 OpenSearch 命中视为孤儿，不能作为正式证据。

### 7.3 系统架构类问题的专用流程

例如用户询问“系统由哪些模块组成”“某功能在哪个模块”“显示链路如何传递”时：

```text
识别 architecture/function/interface 意图
→ 提取系统、构型、版本和功能名称
→ PostgreSQL 查询 icp_functions 获得标准化功能候选
→ OpenSearch 仅过滤 function_locator，执行 BM25 + k-NN + RRF + rerank
→ 用 function_id/module_name/source_ref 回查并合并权威记录
→ 以 PostgreSQL 中可追溯的功能/模块业务 ID 为种子查询 HugeGraph 上下游、多跳接口关系
→ 返回“系统→子系统→模块→功能→接口/输入输出”的结构化答案
→ 附文档编号、版本、页/图来源和原图证据
```

若多个构型的架构不同，答案必须分构型展示或先追问，不能把多个版本拼成一张看似确定的架构。

### 7.4 故障诊断答案约束

答案至少区分：

1. **资料明确记载**：PostgreSQL 权威行及原文直接支持；
2. **跨文档关联推断**：由多个来源或 HugeGraph 关系支持，但原文未直接下结论；
3. **仍需确认**：缺少构型、版本、代码或测量值，或者相关图修订仍为 `provisional`/`quarantined`，尚不能支持正式结论。

证据不足时返回多个候选、匹配依据和能区分候选的补充问题。不得把向量 Top-1 或 rerank Top-1 写成唯一故障结论。

## 8. OpenSearch 索引设计

### 8.1 单一版本化检索投影

运行时只使用稳定 alias：

```text
knowledge_graph_default → knowledge_graph_default_v1
```

主要设计：

- `content`、`title`、`section`、`summary` 等使用 CJK analyzer 进行 BM25；
- `content_vector` 为 1024 维 `knn_vector`；
- HNSW 使用 Lucene engine 和 cosine similarity；
- `doc_type_kwd`、业务 ID、HMC 子码及所有 `*_kwd` 用于精确过滤；
- `_source` 返回时排除大向量字段；
- 开发单节点可用 1 shard、0 replica，生产容量按测量调整。

### 8.2 mapping 升级和 alias 切换

向量维度、analyzer、字段类型或分块策略变化时：

1. 保留当前 alias 和旧物理索引；
2. 创建新版本，例如 `knowledge_graph_default_v2`；
3. 从 PostgreSQL 批量读取，使用指定 BGE-M3 版本重新生成所有投影；
4. 校验总数、按七类数量、随机来源回查、向量维度和代表性检索问题；
5. 短暂停止写入或补齐增量；
6. 原子切换 alias 到 `v2`；
7. 保留 `v1` 一个观察周期后再按审批删除。

不要让一个 alias 同时指向多个非预期写索引。应用启动发现 alias 指向错误版本或向量 mapping 不兼容时应就绪失败，而不是自动覆盖。

## 9. HugeGraph 投影设计

HugeGraph 只解决关系遍历问题，例如：

```text
现象 → 功能 → 模块 → HMC → FMECA 原因/影响
                    ├→ MFL/API
                    ├→ FTA 原因链
                    └→ 历史案例
```

投影要求：

- 顶点使用稳定业务 ID，不用自由文本哈希冒充领域实体；
- 边必须有 `doc_id`、`source_ref`、适用范围、`validation_status` 和生成版本；
- 同名不同构型实体不能无条件合并；
- FTA 与 RBD 使用不同顶点/边语义；
- 删除文档或作废版本时相应投影可按 `doc_id` 重建；
- 图查询返回业务 ID 后仍回 PostgreSQL hydrate 权威详情。

正式图遍历只使用当前有效、已发布的 `auto_validated` 修订，以及兼容保留的 `manual_confirmed` 修订。`provisional` 可以在可视化中浏览和定位原图，但不能支持正式多跳结论；`quarantined` 不进入 HugeGraph 推理投影。`manual_confirmed` 不再是新数据自动入图的前置步骤。

## 10. 模型部署和角色绑定

模型身份、端点和默认角色保存在 PostgreSQL `llm_models` 及 Agent 角色配置中，不在 `.env` 硬编码模型名。

| 角色 | 本地模型 | 关键验证 |
|---|---|---|
| Chat / plan / answer | `qwen3.6:latest`（Ollama） | `/api/chat` 可用、中文工具规划正常、上下文上限符合配置 |
| Vision | 可处理图片的本地 Qwen3.6 实例 | 必须实际验证图片输入；未验证前不能声称 FTA/RBD/架构图自动解析可用 |
| Embedding | `bge-m3:latest`（Ollama） | `/api/embed` 支持批量输入且每条严格为 1024 维 |
| Rerank | `bge-reranker-v2-m3` 本地服务 | 兼容 `/v1/rerank`、`/api/rerank` 或 `/rerank` 之一，返回候选索引和相关性分数 |

应用容器中的 `localhost` 指向应用容器自身。Ollama 和 rerank 若运行在宿主机，模型 `base_url` 必须填写应用容器可达的局域网地址，并限制为内网访问。

模型升级也要版本化：记录模型名/摘要、服务镜像、维度、分块参数、重建时间和评测结果。BGE-M3 版本变化后应全量重建向量；不能在同一物理索引混合新旧向量。

## 11. 迁移实施步骤

### 11.1 迁移前

1. 冻结上传和解析任务，记录当前分支、镜像 ID 和配置；
2. 对 PostgreSQL 做逻辑备份，对 ArtifactStore/旧文件源做一致快照；
3. 运行文件引用审计，记录缺失和孤儿；
4. 统计旧检索记录，但不把缺少 PostgreSQL 主记录的命中列为迁移真源；
5. 确认本地 Qwen3.6、BGE-M3 和 rerank 服务从 app 网络可访问。

### 11.2 文件服务替换

旧 MinIO 仅作为历史迁移源：通过其 API 流式读取对象并写入 ArtifactStore，比较 size 和 SHA-256。不得直接复制 MinIO 私有数据目录中的元数据文件。迁移验证完成前保留只读源卷和精确旧镜像。

### 11.3 检索服务替换

1. 启动空的 OpenSearch 持久化卷；
2. 创建 1024 维版本化索引和 alias；
3. 执行 `scripts/reindex_opensearch.py --dry-run` 清点 PG 权威记录；
4. 执行经变更窗口授权的完整重建；
5. 比较 PG 记录数与投影数，并解释 HMC 双投影等合理倍数；
6. 抽样检查 `doc_id`、业务 ID、通用元数据和 `source_ref`；
7. 运行七类代表性检索和 HMC 精确查询；
8. 通过后才把应用流量切到新 alias。

旧 Elasticsearch 只允许在隔离副本上作为取证/迁移兼容源，不再属于主运行时，不直接挂载唯一旧卷，也不作为新 OpenSearch 的权威输入。

### 11.4 HugeGraph

先从 PostgreSQL 中的显式结构化关系、`auto_validated` 图修订和兼容保留的 `manual_confirmed` 修订重建正式投影。`provisional` 只重建为浏览投影，`quarantined` 保持隔离；整个重建不要求用户逐图确认。

## 12. 回滚方案

| 故障 | 回滚动作 |
|---|---|
| 新 OpenSearch 索引效果异常 | 原子把 alias 切回上一个物理索引；PG 和 ArtifactStore 不回滚 |
| 新 mapping 无法启动 | 保留失败索引用于排查，恢复旧 alias 和上一应用镜像 |
| ArtifactStore 迁移缺件 | 停止写入，使用 manifest 定位并从只读旧源补迁；验证前不删除旧源 |
| PostgreSQL schema/数据异常 | 停止应用，按变更窗口恢复 PG 快照和匹配版本应用；不得从检索索引反推覆盖 PG |
| HugeGraph 投影错误 | 清空受影响投影并从 PG 重建；不影响权威结构化事实 |
| 模型升级效果下降 | 恢复旧模型服务；Embedding 变化时同时恢复匹配的旧 OpenSearch 索引 |

回滚演练必须验证原件可读、PG 精确查询、alias、模型版本和引用链是一套相互匹配的版本。

## 13. 备份与恢复

### 13.1 必须备份

- PostgreSQL：使用 `pg_dump`/受控快照，包含领域事实、文档状态和模型配置；
- ArtifactStore：在停止新写入或使用一致文件系统快照时备份整个目录，包括 `.trash`；
- 部署清单：Compose、`.env` 的安全副本、镜像摘要、模型清单和迁移 manifest；
- HugeGraph：使用产品支持的导出/快照，或停服务后做一致卷快照。

OpenSearch 可以从 PG 重建，但为缩短恢复时间可使用 OpenSearch snapshot。不要在 OpenSearch 运行写入时直接复制其数据目录作为可靠备份。

### 13.2 恢复顺序

```text
恢复 PostgreSQL
→ 恢复 ArtifactStore 并运行引用审计
→ 恢复或重建 OpenSearch
→ 恢复或重建 HugeGraph
→ 恢复模型服务与角色绑定
→ 启动 app 并检查 /readyz
→ 执行七类抽样和诊断回归
```

## 14. 健康检查、监控与容量

### 14.1 就绪条件

- `/livez`：应用进程存活；
- `/readyz`：PostgreSQL、OpenSearch、HugeGraph 和 ArtifactStore 均可用；
- OpenSearch：集群为 `green` 或单节点预期的 `yellow`，alias 与 1024 维 mapping 正确；
- ArtifactStore：挂载目录可写，原件目录未被静态公开；
- 模型：Chat、Embedding、Rerank 分别执行最小真实请求，而不只检查端口；
- 严格依赖模式下不得静默回退到内存数据库或临时搜索索引。

### 14.2 监控指标

- 上传/解析成功率、失败阶段和重试数；
- PG 到 OpenSearch 的待投影数、孤儿数和更新时间差；
- 七类记录数、向量数、HugeGraph 顶点/边数；
- BM25、k-NN、rerank 延迟及降级次数；
- ArtifactStore 总量、孤儿、垃圾保留量和磁盘余量；
- Ollama/rerank 请求错误、GPU/CPU 内存和并发队列；
- 诊断中“资料明确记载/推断/待确认”的比例和人工复核反馈。

## 15. 安全与本地部署边界

当前 Compose 中关闭 OpenSearch 安全插件仅适用于受控单机开发环境。生产或正式内网部署必须：

- 使用强 PostgreSQL 密码，不把 5432/5433 暴露到不可信网络；
- 为 OpenSearch 启用认证和 TLS，或完全置于受控内部网络；
- 为 HugeGraph、Hubble、Ollama 和 rerank 服务设置网络访问控制；
- 只公开主应用端口，管理端口优先绑定回环地址或防火墙白名单；
- `.env`、API key、备份和模型配置按密钥管理，不写入 Git 和日志；
- ArtifactStore 目录采用最小读写权限，`/images` 只暴露工程图子目录；
- 上传文件限制扩展名、大小和路径，禁止路径穿越，解析过程使用临时目录；
- 镜像和模型使用固定版本或摘要，离线交付前做依赖和许可证清单；
- 日志避免输出原文全文、模型密钥和敏感故障数据。

LocalFS 适合当前单机部署，简单、可审计且没有额外服务。若未来需要多机高可用，可以在不改变业务 storage key 的前提下为 ArtifactStore 增加共享文件系统或开源对象存储后端；当前无需提前增加此复杂度。

## 16. 验收标准

### 16.1 基础设施

- [ ] PostgreSQL 15、OpenSearch、HugeGraph/Hubble 和 app 使用持久化目录并通过健康检查。
- [ ] OpenSearch 同时提供 BM25 和 1024 维向量，不存在 Milvus 运行时依赖。
- [ ] Qwen3.6、BGE-M3、BGE-Reranker-v2-M3 均从 app 运行网络完成真实调用。
- [ ] `/readyz` 在任一权威依赖不可用时明确失败。

### 16.2 数据和证据

- [ ] 用户侧严格只有七类文档和一个统一上传入口。
- [ ] 七类原件均能由 ArtifactStore 读取，工程图可通过 `/images` 在文档证据上下文查看。
- [ ] 七类结构化事实能够按 `doc_id` 和业务 ID 从 PostgreSQL 查询。
- [ ] 每个 OpenSearch 命中都能回查 PG 主记录或明确的原文片段。
- [ ] 文档编号、系统、构型、版本、来源、状态和日期已从 PG 继承到投影精确字段。
- [ ] `auto_validated` 图可进入正式 HugeGraph 关系；`provisional` 只供浏览；`quarantined` 不入推理图；`manual_confirmed` 仅作为历史兼容状态。

### 16.3 检索和诊断

- [ ] BM25 与 k-NN 分别召回，RRF 后去重，全候选 rerank 后再取 `top_k`。
- [ ] Embedding/rerank 降级有明确记录，不能无声改变排序语义。
- [ ] 完整 HMC/三码组合走 PostgreSQL 精确查询。
- [ ] 架构问题返回标准化系统/模块/功能/接口和来源，不只返回自由文本。
- [ ] FTA/RBD 计算由确定性代码完成，缺少参数时不猜数值。
- [ ] 模糊现象在证据不足时返回多个候选、依据和补充问题。
- [ ] 工具按本轮目标字段定向授权，首批结果后最多执行一批自适应补查，不退化成固定七类全扫描。

### 16.4 兼容与运维

- [ ] Dify 两个既有路径保持可用。
- [ ] `/gallery` 没有恢复；图片解析和证据访问仍可用。

## 17. 明确的持续完善项

本方案建立了数据和运行边界，但以下内容仍需用脱敏真实样例和问题集持续验证：

- Word/Excel 多级表头、跨页表头和复杂图像的解析覆盖率；
- 不同机型、构型、软件版本的标准化编码与冲突处理；

- 检索召回率、rerank 排序质量和诊断答案的人工评测；
- Dify 旧兼容链路向七类专用检索迁移的独立方案。

在这些项目通过真实环境验证前，不应宣称已经达到正式维修决策或适航结论所需的可靠性。
