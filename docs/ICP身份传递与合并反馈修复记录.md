## 事实依据与修改

### 1. 编号确实在传递时丢失

通过只读 `/api/v1/icp-domain/functions/{doc_id}` 核对：实际 FUNC-230 行的 `module_id` 是 MOD-GPP-MSM，`parent_function_id` 是 FUNC-200。`icp_diagnosis._direct_evidence` 原来没有把这两个字段放入功能记录的 `answer_fields`。

现在直接保留 PG 返回的原值，作者与审核使用同一份字段视图。空字段仍为空，不根据中文名称、邻近记录、模型判断或旧会话补造 ID。不修改原数据库，不把同名关系提升为显式关系。

### 2. 联合引用复用现有能力

原引用检查本来支持一句话中的多个作者引用，因此没有再新增关联器、跨记录自动合并或事后补引用流程。新增正反测试验证：明确所属 ID 的功能记录可以与组件记录共同引用，两份来源和原文保留；只引用同名邻居、从前文借用 ID、借相似报码或邻居数值仍失败。

明确 ID 能证明部件关联，但不自动证明故障模式、版本/构型、维修方法或因果关系相同。记录级语义是否支持联合结论仍由审核判断，不能把“编号都出现了”当成整句事实成立。

### 3. 一次反馈已发现的独立问题

确定性引用检查改为在同一份不可变草稿上收集各片段的身份、引用、授权和数值问题，不在第一处错误即中止检查；保留原失败接口，内部复用同一套检查，不维护两个判据。

整篇审核不再因为语义问题已存在就跳过引用/权限检查。将已发现的问题一起交给作者的唯一一次修订；重新检查修订全文，错误或未核验答案不发布。未知引用不会被拿去读取不存在的记录；无效协议仍属协议失败，`unverified` 仍不发布也不冒充内容通过。无法判断的语义不由代码关键词兜底。

## 本批仍未过关的地方

`explicit-component/valid`：用户问“MOD-019 的数据保存功能异常时，会直接影响什么？”，来源明确所属部件并记载“配置数据无法读取”，回答“MOD-019 对应的直接失效表现是配置数据无法读取”。新审核认为“表现”不能回答“影响”，要求额外下游后果，因而拒绝。

本批判定这是过度要求：配置读取受阻已经是该功能的直接影响，用户没有强制要求进一步的系统级后果；不能因为来源字段叫 `failure_symptoms` 就自动追加下游后果义务。这是有理由的开发者复核，不是独立领域专家签认。原题、原稿、来源和拒绝报告均保留，未改题求通过。

因此仍存在语义审核误拒，新增的实测前置验收没有通过，按事先说明暂停进入 19 例，不继续改提示后反复试到通过。昨晚架构整改已经覆盖“区分事实与推断、修订后完整重审”这些目标，但代码落地不等于效果达标。本批补齐传递和反馈缺陷，也不能宣称这两项目标彻底完成。

恢复后仍采用完整 19 例、历史失败优先、首败即停；100 例保持暂停。本批未改变该规则。
