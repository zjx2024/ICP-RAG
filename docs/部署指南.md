# ICP-RAG 部署指南

本文档说明 ICP 故障诊断知识库在单机 Linux 上的本地自部署方式。

## 1. 运行架构

```text
浏览器
   │ :19999
   ▼
FastAPI / React
   ├── PostgreSQL      权威结构化事实
   ├── OpenSearch      CJK BM25 + BGE-M3 向量检索
   ├── HugeGraph       显式关系与自动校验分级投影
   ├── ArtifactStore   原文、解析产物和工程图证据
   │      └── LocalFS: /app/data/artifacts
   └── 本地模型服务
          ├── Ollama: Qwen3.6 + BGE-M3
          └── BGE-Reranker-v2-M3 rerank API
```

ArtifactStore 在 app 进程内运行，不是独立微服务，因此不占用网络端口。

| 服务 | 宿主机端口 | 用途 |
|---|---:|---|
| FastAPI | 19999 | 主服务，容器内端口 9999 |
| PostgreSQL | 5433 | 文档、任务、领域事实和模型配置 |
| OpenSearch | 9201（本机） | 关键词、过滤和 1024 维向量检索 |
| HugeGraph | 8082 | 图数据库 |
| Hubble | 18089 | 图谱可视化 |

MinIO 已从主运行时组合中移除。历史 MinIO 卷仅作为迁移源保留。
当前运行时也不部署 Milvus；OpenSearch 在同一索引中完成全文与向量检索。

Compose 当前固定的主要服务版本为 PostgreSQL 15、OpenSearch 3.6.0、HugeGraph 1.7.0
和 Hubble 1.7.0。模型服务由宿主机或内网节点提供，不计入上述五个项目容器。

## 2. 前置条件

| 项目 | 要求 |
|---|---|
| 操作系统 | Linux（Ubuntu/CentOS 等） |
| Docker | 20.10+ 且安装 Docker Compose v2 |
| Python | 3.10+（仅本地热启动或迁移需要） |
| 内存 | 基础设施至少 8 GB；Qwen3.6、Embedding 和 rerank 的内存/显存另行按实际权重评估 |
| 磁盘 | 至少 50 GB 可用空间，产品数据应单独评估 |

验证 Docker：

```bash
docker --version
docker compose version
```

非 root 用户需要有权访问 Docker daemon，并对 `volumes/artifacts` 具有读写权限。

## 3. 目录和持久化数据

```text
ICP-RAG/
├── backend/                         FastAPI、解析器和智能体
├── frontend/                        React 源码
├── docker-compose.yml
├── Dockerfile
├── requirements.txt                 主运行时依赖
├── requirements-migration.txt       仅历史 MinIO 迁移使用
├── scripts/audit_artifact_refs.py   PG 与 LocalFS 只读一致性审计
├── scripts/migrate_minio_to_localfs.py
└── volumes/
    ├── postgres/                    PostgreSQL
    ├── opensearch/                  OpenSearch 当前检索投影
    ├── hugegraph/                   HugeGraph
    ├── artifacts/                   ArtifactStore LocalFS
    ├── migration/                   迁移 manifest
    ├── minio/                       历史 MinIO 迁移源，未验证前不删除
    └── es/                          历史 Elasticsearch 回滚源，不被当前运行时挂载
```

ArtifactStore 宿主机和容器路径的映射为：

```text
./volumes/artifacts  <->  /app/data/artifacts
```

实际布局：

```text
volumes/artifacts/
├── .staging/
├── .trash/
├── icp/
├── documents/
└── images/
```

`/images` 只对应 `images/` 子目录，不会静态暴露原始文档。

## 4. 环境变量

`.env` 不随 Git 上传。仓库提供 `.env.example`；也可不创建 `.env` 而使用
Compose 默认值。`start.sh` 会创建或更新其中的 `SERVER_IP`。

```bash
cp .env.example .env
```

基础模板包含：

```env
OPENSEARCH_HOST=localhost
OPENSEARCH_PORT=9201
OPENSEARCH_SCHEME=http
OPENSEARCH_VERIFY_CERTS=false
OPENSEARCH_INDEX_ALIAS=knowledge_graph_default
OPENSEARCH_INDEX_VERSION=v1
OPENSEARCH_REQUEST_TIMEOUT=60
STRICT_DEPENDENCIES=true

POSTGRES_HOST=localhost
POSTGRES_PORT=5432
POSTGRES_USER=postgres
POSTGRES_PASSWORD=replace-with-a-strong-password
POSTGRES_DB=knowledge_graph

APP_UID=1000
APP_GID=1000

ARTIFACT_BACKEND=local
ARTIFACT_STORAGE_DIR=./volumes/artifacts
ARTIFACT_TRASH_ENABLED=true
IMAGE_STORAGE_DIR=./volumes/artifacts/images

HUGEGRAPH_HOST=localhost
HUGEGRAPH_PORT=8081
HUGEGRAPH_GRAPH_NAME=hugegraph

SERVER_HOST=0.0.0.0
SERVER_PORT=9999

MODEL_TEMPERATURE=0.7
MODEL_MAX_TOKENS=262144
MODEL_TIMEOUT=3000
MODEL_TOP_P=0.1
EMBEDDING_DIM=1024
CHUNK_SIZE=512
CHUNK_OVERLAP=50
```

Compose 会覆盖容器内的服务主机名和 ArtifactStore 绝对路径。模型身份与
端点保存在 PostgreSQL `llm_models` 表，不在 `.env` 中配置。PostgreSQL 服务和
app 使用同一组 `${POSTGRES_*}` 插值，因此修改密码不会造成两端不一致。

若本机 5433 已被其他项目占用，可在 `.env` 增加：

```env
COMPOSE_FILE=docker-compose.yml:docker-compose.local.yml
```

该覆盖把宿主机 PostgreSQL 端口改为 5434；`start_server.sh` 会从正在运行的
Compose 项目自动探测该端口。

## 5. 启动

### 5.1 本地热启动

启动基础设施：

```bash
./start.sh
```

无参数时，`start.sh` 只启动 PostgreSQL、OpenSearch、HugeGraph 和 Hubble。
然后启动本地 FastAPI：

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
./start_server.sh
```

访问 `http://localhost:19999`。

### 5.2 Docker 完整部署

```bash
mkdir -p volumes/artifacts/images
docker compose -p icp up -d --build
```

该命令运行 postgres、opensearch、hugegraph、hubble 和 app 五个容器。
只重建 app：

```bash
./restart-app.sh
```

## 6. 健康检查

```bash
docker compose -p icp ps
pg_isready -h localhost -p 5433 -U postgres
curl -fsS http://localhost:9201/_cluster/health
curl -fsS http://localhost:8082/graphs/hugegraph
curl -fsS http://localhost:19999/livez
curl -fsS http://localhost:19999/readyz
```

检查 alias 和向量 mapping：

```bash
curl -fsS http://localhost:9201/_alias/knowledge_graph_default
curl -fsS http://localhost:9201/knowledge_graph_default_v1/_mapping
```

`/readyz` 必须同时确认 PostgreSQL、OpenSearch、HugeGraph 和 ArtifactStore；依赖异常时
不能回退到进程内临时数据库或搜索索引继续对外声明就绪。

确认 LocalFS 挂载：

```bash
docker compose -p icp exec app sh -c 'test -w /app/data/artifacts && test -d /app/data/artifacts/images'
```

在 app 容器中执行只读引用审计（自动复用容器的 PostgreSQL 环境变量和挂载路径）：

```bash
# 日常/发布验收：PG 引用的每个 key 都必须存在
docker compose -p icp exec -T app \
  python scripts/audit_artifact_refs.py \
  --artifact-root /app/data/artifacts

# 深度盘点：同时报告 LocalFS 孤儿；不会删除或修改任何数据
docker compose -p icp exec -T app \
  python scripts/audit_artifact_refs.py \
  --artifact-root /app/data/artifacts \
  --check-orphans --json
```

退出码 `0` 表示一致，`1` 表示发现引用问题或本次启用检查发现孤儿，`2` 表示
数据库、挂载或权限问题导致审计未完成。`.staging` 和 `.trash` 不计入孤儿。

## 7. 配置本地模型

新数据库中没有模型时，解析、图谱生成和诊断会返回“未配置模型”。

1. 打开 `http://<服务器 IP>:19999`。
2. 进入“系统设置”。
3. 配置 Chat/Vision、Embedding 和 Rerank 模型。
4. 为各角色指定默认模型。

| 角色 | 模型名 | `base_url` 要求 |
|---|---|---|
| Chat / plan / answer | `qwen3.6:latest` | 指向 app 容器可访问的 Ollama 根地址 |
| Vision | 支持图片输入的本地 Qwen3.6 实例 | 保存前必须实际测试图片输入；未通过时图像自动解析不可验收 |
| Embedding | `bge-m3:latest` | Ollama 根地址，应用调用 `/api/embed`，每条必须为 1024 维 |
| Rerank | `bge-reranker-v2-m3` | 本地服务应支持 `/v1/rerank`、`/api/rerank` 或 `/rerank` 之一 |

先从模型宿主机验证 Ollama：

```bash
curl -fsS http://127.0.0.1:11434/api/tags
curl -fsS http://127.0.0.1:11434/api/embed \
  -H 'Content-Type: application/json' \
  -d '{"model":"bge-m3:latest","input":["ICP 故障诊断连通性测试"]}'
```

再从 app 容器使用实际填写的局域网地址验证；容器内的 `localhost` 是 app 本身，
不能代表模型宿主机：

```bash
docker compose -p icp exec -T app python -c \
  "import urllib.request; print(urllib.request.urlopen('http://<模型主机>:11434/api/tags', timeout=5).status)"
```

Rerank 没有统一健康路径，应使用其真实 API 发送至少两个候选的请求，确认响应包含候选
`index` 和相关性分数。只检查端口打开不算模型联调通过。

恢复旧 `volumes/postgres` 时，`llm_models` 和 Agent 配置会随数据库恢复。

## 8. 旧 MinIO 数据迁移

### 8.1 保护源数据

不要直接拷贝 `volumes/minio` 中的 `xl.meta`。MinIO 可以将对象内联在其
私有元数据中，必须通过 MinIO API 读取。

建议：

1. 停止 app 和所有后台解析任务。
2. 备份 PostgreSQL、`volumes/minio` 与 `app/storage/images`。
3. 用 `docker inspect --format '{{.Image}}' <旧容器>` 保存精确旧镜像 ID。
4. 复制 MinIO 卷，用该镜像 ID 在可写副本上启动迁移源；不要使用 `latest`。
5. 迁移和验证完成前，原卷保持只读且不删除。

可复现迁移源示例：

```bash
LEGACY_MINIO_IMAGE="$(docker inspect --format '{{.Image}}' icp-minio-1)"
sudo cp -a volumes/minio volumes/minio-migration-copy
docker run -d --rm --name icp-minio-migration-source \
  -p 127.0.0.1:9002:9000 -p 127.0.0.1:9003:9001 \
  -e MINIO_ROOT_USER="$MIGRATION_MINIO_ACCESS_KEY" \
  -e MINIO_ROOT_PASSWORD="$MIGRATION_MINIO_SECRET_KEY" \
  -v "$PWD/volumes/minio-migration-copy:/data" \
  "$LEGACY_MINIO_IMAGE" server /data --console-address ':9001'
```

### 8.2 执行迁移

```bash
python -m venv .venv-migration
source .venv-migration/bin/activate
pip install -r requirements-migration.txt

# 清点，不读取对象内容
python scripts/migrate_minio_to_localfs.py --dry-run

# 流式迁移 MinIO + 旧 app/storage/images，支持中断后继续
MIGRATION_MINIO_ENDPOINT=localhost:9002 \
MIGRATION_MINIO_ACCESS_KEY=admin \
MIGRATION_MINIO_SECRET_KEY='replace-me' \
python scripts/migrate_minio_to_localfs.py --resume

# 重读源和目标，全量比较 size + SHA-256
python scripts/migrate_minio_to_localfs.py --verify-only
```

如果只需迁移旧本地图片：

```bash
python scripts/migrate_minio_to_localfs.py --skip-minio --resume
```

默认 JSONL manifest 位于 `volumes/migration/minio-to-localfs.jsonl`。迁移保留原逻辑
key，因此 PostgreSQL 中的历史 `minio_path` 列无需改写。更详细的一致性、
回滚和第二阶段 schema 设计见
[`ArtifactStore本地文件存储方案.md`](ArtifactStore本地文件存储方案.md)。

## 9. Elasticsearch 到 OpenSearch

当前运行时不读取旧 Elasticsearch。OpenSearch 是可重建投影，迁移以 PostgreSQL
结构化真源、ArtifactStore 原件和 BGE-M3 重新生成向量为准，不直接复制 ES 内部数据目录，
也不把缺少 PostgreSQL 主记录的孤儿命中导入新索引。

```bash
# 只统计将从 PostgreSQL 重建的投影，不写 OpenSearch
docker compose -p icp exec -T app \
  python scripts/reindex_opensearch.py --dry-run

# 清空当前 alias 指向的投影后完整重建；重建前应先做 PG 快照
docker compose -p icp exec -T app \
  python scripts/reindex_opensearch.py --reset --yes --batch-size 16
```

运行时只访问稳定 alias `knowledge_graph_default`，物理索引使用版本名
`knowledge_graph_default_v1`。下一次 mapping 变更应创建 `v2`、完成全量重建和审计后再切 alias，
不要在原索引上原地修改向量维度。

旧 `volumes/es` 保留为回滚/取证源。如确需查看，先制作副本，再启动完全隔离的旧服务：

```bash
sudo cp -a volumes/es volumes/es-migration-copy
sudo chown -R 1000:1000 volumes/es-migration-copy
docker compose -f docker-compose.legacy-es.yml \
  --profile legacy-migration up -d legacy-elasticsearch
curl -fsS http://127.0.0.1:9202/_cluster/health
```

这个可选容器不加入主网络、不被 app 依赖，且绝不能直接挂载唯一的旧数据卷。

## 10. 备份与整机迁移

### 10.1 一致性备份

为避免备份过程中出现跨存储时间差，先停止 app 和后台解析任务，再按顺序执行：

```text
pg_dump 生成 PostgreSQL 逻辑备份
→ 一致复制或快照 volumes/artifacts（包括 .trash）
→ HugeGraph 导出，或停 HugeGraph 后快照其数据卷
→ OpenSearch snapshot（可选，因为可以从 PG 重建）
→ 备份迁移 manifest、Compose、镜像/模型版本清单
```

不要在 OpenSearch 或 HugeGraph 正在写入时直接复制其数据目录并将其当作可靠备份。
ArtifactStore 的 `.trash` 应与主目录一同备份，否则无法恢复误删文件。`.env` 需要单独加密
保管，不应随普通代码或无访问控制的迁移包分发。

最小 PostgreSQL 逻辑备份示例：

```bash
docker compose -p icp exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "icp-postgres-$(date +%Y%m%d-%H%M%S).dump"
```

### 10.2 导出镜像

```bash
./export-images.sh
```

默认导出 app、postgres、opensearch、hugegraph 和 hubble 五个运行时镜像。
若旧 MinIO 尚未完成迁移，可选保留当前机器的旧镜像：

```bash
LEGACY_MINIO_IMAGE="$(docker inspect --format '{{.Image}}' icp-minio-1)" \
INCLUDE_LEGACY_MINIO_IMAGE=1 ./export-images.sh
```

脚本拒绝 `:latest`；该精确旧镜像只用于卷副本迁移，不应重新加回主 Compose。

### 10.3 新机器恢复

```bash
# 逐个加载镜像
gunzip -c images/knowledge-graph-app.tar.gz | docker load
gunzip -c images/postgres.tar.gz | docker load

# 拷贝整个 volumes/ 后修复已知容器用户权限
docker run --rm -v "$PWD/volumes/opensearch":/data alpine chown -R 1000:1000 /data
docker run --rm -v "$PWD/volumes/postgres":/data alpine chown -R 999:999 /data

# artifacts 必须对运行 app 的 uid/gid 可读写
mkdir -p volumes/artifacts/images

docker compose -p icp up -d
```

恢复后先运行 ArtifactStore 引用审计，再恢复或重建 OpenSearch，最后恢复/重建 HugeGraph。
模型权重不属于项目 `volumes/`；新机器还必须恢复精确模型版本，并重新验证 Chat、Embedding
和 Rerank 的真实请求。

## 12. 故障排查

### 12.1 ArtifactStore 无法写入

```bash
ls -ld volumes/artifacts volumes/artifacts/images
docker compose -p icp exec app sh -c 'id; touch /app/data/artifacts/.write-test && rm /app/data/artifacts/.write-test'
```

不要将 `ARTIFACT_STORAGE_DIR` 指向容器未挂载的可写层，否则重建容器后会丢失文件。

### 12.2 图片 404

- 检查 `IMAGE_STORAGE_DIR=/app/data/artifacts/images`。
- 检查旧 `app/storage/images` 是否已迁移。
- 确认数据库 `image_url` 的 `/images/...` 相对路径与文件相符。

### 12.3 模型未配置

- 检查 `llm_models` 是否包含 Chat/Vision、Embedding 和 Rerank 角色。
- 确认 Ollama 端点从 app 容器内可访问。
- 确认 `qwen3.6:latest`、`bge-m3:latest` 和 BGE-Reranker-v2-M3 权重已下载且服务版本匹配。
- Embedding 报维度错误时不要修改 OpenSearch mapping 迁就错误模型；必须恢复 1024 维
  BGE-M3，或按新向量空间创建新版本索引并全量重建。

### 12.4 端口被占用

```bash
sudo lsof -i :19999
sudo lsof -i :5433
sudo lsof -i :9201
```

## 13. 安全加固

当前 Compose 关闭 OpenSearch security plugin，适用于受控单机开发环境，不适合直接暴露到
不可信网络。正式内网部署至少完成：

- 修改 PostgreSQL 默认密码，仅对 app 网络或管理白名单开放数据库；
- 为 OpenSearch 启用认证/TLS，或完全取消宿主机公开端口；
- 限制 HugeGraph、Hubble、Ollama 和 rerank 的访问来源；
- 主机防火墙默认只公开 FastAPI 业务端口，管理端口优先绑定 `127.0.0.1`；
- `.env`、备份、模型配置和 API key 不进入 Git，日志不打印密钥和原文全文；
- `volumes/artifacts` 使用最小 UID/GID 权限，只有 `images/` 通过 `/images` 暴露；
- 上传限制文件扩展名和大小，保留路径穿越检查与临时目录隔离；
- 交付时固定镜像/模型版本或摘要，并归档实际使用组件的许可证清单。

## 14. 部署验收清单

- [ ] Docker 模式下 5 个容器正常运行。
- [ ] `http://localhost:19999` 返回 200。
- [ ] `/readyz` 中 PostgreSQL、OpenSearch、HugeGraph、ArtifactStore 全部为 `ok`。
- [ ] OpenSearch alias 指向 `knowledge_graph_default_v1`，映射为 1024 维 `knn_vector`。
- [ ] OpenSearch 同时完成 BM25 与 BGE-M3 k-NN 召回，运行时不存在 Milvus 容器、卷或 SDK。
- [ ] `volumes/artifacts` 挂载到 `/app/data/artifacts` 且可读写。
- [ ] 原文上传后宿主机 LocalFS 出现对应 key。
- [ ] `/images` 可访问工程图，但无法静态访问原始文档。
- [ ] 七类文档上传、原文查看、解析和删除正常。
- [ ] Dify 的 `/api/v1/dify/server-info` 和 `/api/v1/dify/retrieval` 未被破坏。
- [ ] Qwen3.6、BGE-M3 和 BGE-Reranker-v2-M3 均从 app 网络完成真实请求。
- [ ] BGE-M3 批量 embedding 每条严格为 1024 维，rerank 返回有效候选索引和分数。
- [ ] 历史 MinIO 迁移 manifest 无错误，`--verify-only` 通过。
- [ ] `audit_artifact_refs.py` 返回 0；深度孤儿报告已人工复核。
- [ ] 重建 app 容器后原件与图片仍存在。
- [ ] PostgreSQL 恢复、ArtifactStore 审计、OpenSearch 重建/alias 回滚已完成演练。
