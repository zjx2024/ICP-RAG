## 3. 根因及证据

### 3.1 审核收敛成了一次高负担的结构化再生成，缺少校验反馈闭环

代码：`backend/agent/nodes/answer.py:816`、`:914`；`backend/agent/answer_review.py:380`。

当前过程是：初稿 → 模型一次性输出修订正文、断言类型、字段路径/引文、来源归属、会话/观察绑定、目标覆盖关系 → 机械验证。任何验证异常都抛出 AnswerGenerationError；具体异常不再反馈给模型修正。

这确实删除了多编辑器，但只是把多种责任集中到一个复杂响应中。模型不仅要解释问题，还要手工维护多张相互引用的表。`format="json"` 保证的也不是这个完整嵌套协议，更不保证语义。

此次 RBD 重放输出四个单元：三个回答主体、一个查询/推断边界说明。goals 只关联前三个，第四个没有被关联，整答因此拒发。此前 R3b 八轮诊断中也有四轮因相同的孤立单元问题拒发。

这不意味着第四段或前三段可以直接放行；该提案另外存在语义支持不足。它说明：文档中的“有界修订”实际被实现为一次预先自修订，而不是对可定位错误提供一次反馈修订。

### 3.2 完成度协议把合法边界回答结构性地排除在 full 之外

代码：`backend/agent/answer_review.py:350`。

`answered` 强制至少关联 fact 或 conversation_reference；仅 source_boundary 无论是否完整回答本轮边界问题都不合格。partial/unanswered 又必须绑定缺口说明。

本轮以人工构造的通用协议数据执行纯校验探针，无模型、无业务查询：

| 输入 | 当前校验结果 |
|---|---|
| 有字段支持且目标关联完整的普通事实 | full |
| 上项增加一个同样有依据、但未关联目标的单元 | 整答拒绝 |
| 有查询观察支持的“本次限定查询未找到匹配条目”，对“本次查到了吗”标 answered | 拒绝：不是完整答案 |
| 相同正文、来源，仅把 answered 改为 partial | 接受，但固定记 partial |

“没找到目标事实”不必然等于“没有回答问题”。当问题本身就是查询边界、资料能否证明某结论时，否定性回答可以是完整答案。去掉自然语言固定词，不代表所有代码约束都合理；这里仍用粗粒度类型代替了完成度语义。

### 3.3 过度拒发与语义漏检同时存在，不能只降低校验强度

代码：`backend/agent/citation_binding.py:85`、`backend/agent/answer_review.py:270`。

字段校验检查“指定字段中确有该引文”，不判断引文是否支持整段含义。含义判断交给模型本身合理，但目前模型同时改写答案、分类、绑定并自报已审核，没有足够可靠的独立反馈。

此次 RBD 提案把“不能替代 FTA/FMECA/MFL/HMC、不能提供根因和维修程序”的论述绑定到结构摘要/串并联表达式。该表达式可支持成功结构，却不能单独证明这些方法论边界。校验已通过所有单元绑定检查，最终才因孤立目标单元拒发。

此次成功发布的 HMC 重放还把“HMC/MFL 关联未确认”的查询状态和适用性免责混在 disclaimer 单元里，未提供 observation_bindings。并非据此断言内容事实错误，而是说明一个模型自报的 kind 就能绕过本应执行的观察来源检查。

因此，“未知引用/错行继续拒绝”必须保留；同时要减少手工维护协议的负担，核实实际命题支持关系。不能发布未经审核的初稿，也不能单纯删除孤立段落来提高通过率。

### 3.4 本轮目标虽被保留，却没有贯穿全部规划与证据选择

代码：`backend/agent/nodes/adaptive_tools.py:1343`、`:1379`、`:1407`；`backend/agent/nodes/answer_evidence_context.py:90`；`backend/agent/nodes/answer_record_scope.py:27`。

R2 已让回答提示直接看到当前原问题和自然语言分问。但补查仍消费意图、必答字段及字段到工具的映射；答案之前仍经过门禁、领域过滤、记录族选择和窗口选择。不能把“提示词不按字段列栏目”视作“整个系统不再由字段驱动”。其中身份/适用性过滤有必要，不能一并删除，但相关性选择与权限校验仍需更明确分工。

原 19 例的 RBD 边界追问：四个自然语言分问与 source_capability/source_limitation 已识别，intent 却为 entity_profile；首次 rbd_query 已返回一条记录，补查仍执行 HMC/FMECA/MFL/历史，历史返回 12 条邻近记录。

此次隔离重放最终生成上下文只保留一条 RBD 引用，说明已有领域过滤确实发挥了作用；不能据跨域工具调用就声称这次又把所有邻居写入答案。但无效补查、摘要噪声和路径复杂度仍存在，尚未实现“围绕本轮缺口的最小查询”。

### 3.5 精确回读有效，但不等于完整会话与回答目标达成

原 19 例中的正面证据：

- HMC 首问精确命中 `91810001**0001`，症状和维修证据均获批准；本轮不能再归因为该组合没查到。
- 历史追问按 doc_id + HIS-SYN-011 回读，anchor_reads=found，返回一条原案例，仍在回答阶段失败。R4 修复了旧案例掉出关键词 Top-N 的问题，但没有解决发布稳定性。
- 架构完整列表及数量核对两轮通过，纯引用发布不再删除成员的改动有实际收益。

当前会话机制主要是有界消息窗口、实际引用锚点和自然语言交付清单，不是完整、已验收的诊断 CaseContext。生成/审核窗口仍为最多 16 条消息、单条最多 6000 字、正文总预算 18000 字；窗口外的候选、反证和未决事项没有完整持久状态证明。已交付目标也依赖本轮审核成功，拒发会阻断后续锚点更新。

上下文密度是待验证的放大因素，而非已独立证明的全部根因：R3b 八轮生成提示为 8586–61978 字符；此次仅一条可引 RBD 的生成提示仍为 13861 字符，其中 context 9324 字符。它们包含审计/查询覆盖等信息；尚未通过同状态简化上下文的配对实验量化其影响，不能直接归因为超出模型上下文窗口。

## 5. 为什么参考了成熟做法仍然失败

外部资料提供设计原则，不为本项目的模型、数据和协议提供效果保证：

- Anthropic 强调从简单可组合流程开始，通过实际测量决定复杂度；审核迭代的前提是有明确标准与有用反馈，不是每次强制生成复杂自证清单。[原文](https://www.anthropic.com/engineering/building-effective-agents)
- 上下文工程强调必要且高信号的材料，避免用冗长规则/边界案例堆叠替代清晰接口。[原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Azure 的参考流程强调面向问题的聚焦子查询、重排、统一证据和引用；该功能文档本身标明 preview，不能称为已验证的本地航空诊断方案。[原文](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview)
- GraphRAG 按问题结构提供不同检索方式，并保留基础向量 RAG 作为比较对象；引入图或多阶段流程本身不是收益证明。[原文](https://microsoft.github.io/graphrag/query/overview/)

本项目的偏离是：把“少节点”近似成“低复杂度”，把“字段有引文”近似成“事实已支持”，把“代码替换完成”近似成“职责目标完成”。计划曾要求配对净收益再验收，但已有配对结果存在裁判异常，未形成新链路稳定优于旧链路的证据。这不是在成熟方案已完整落实后发生的无法解释的退步。

用户允许暂时不看分数、继续结构替换，不代表这些验收条件可以自动标为通过。进度报告应更明确区分代码迁移与行为达标；此前口径需要纠正。

## 6. 测试本身的剩余问题

- 1419 项后端测试证明的是已编码约束和 mock 协议，不证明模型能稳定生成这些协议。部分新测试明确把“恰好两次调用、失败不重试”固化为成功条件，因此不能用它们证明这个调用设计合理。
- 两个裁判均为 34/36，且相同两项漏判；没有资格自动宣布总体语义验收通过。
- MFL 历史追问已回答“最终位于哪里、怎样验证恢复”，却因缺少几项中间诊断细节被 expected_dimension 判失败。这里有把参考材料的全部细节当作必答项的风险，应独立复核问题与 rubric；本轮不更改 gold，也不先改分数。
- 与早期弱关键词断言的 13/19 或 17/19 不是同口径比较，但 16 次真实拒发无需依靠裁判即可判断不可接受。
- 原 16 次失败缺少安全、结构化的审核失败原因码；需要可审计的错误分类与私有提案记录，不必把内部稿或敏感资料公开到 SSE。

## 7. 建议的纠偏顺序（本轮未实施）

1. 先把审核协议当作待验证设计：区分事实错误、支持关系不足、输出格式错误、目标关联错误、合法无资料回答；不能都归为同一个整答失败。
2. 缩小模型须手工维护的协议。证据句柄、字段坐标及引用映射由程序准备，模型负责选择、综合和语义核验；当前问题目标保持唯一来源，不能让审核另造一套目标定义。
3. 在同一审核边界内提供一次基于具体失败反馈的修订，校验后仍不合格就如实终止或交付已经完整核验且不破坏依赖关系的部分。禁止裸稿回填、关键词补写和多编辑器串联。
4. 将方法/系统能力说明、查询状态、用户观察、历史表述与工程事实分清来源种类；合理的边界答案可完整回应边界问题，不为得到 full 强迫它冒充工程事实。
5. 补查依据本轮未解决的信息目标和相关对象，不把允许使用的工具当作必须遍历的工具；保留 PG 身份、构型、版本和计算授权硬边界。
6. 用小而混合的诊断集先验证完整发布、命题支持和安全，包含同义改写、随机身份、正常问题与反例；做同模型同证据配对，不能只有失败题。协议稳定且人工复核通过，再恢复 19 例；19 例达到既定关口后才恢复 100 例及重复评测。

优先保留已有效的 PG、七类工具、确定性算法、纯引用渲染和接口兼容，不重新推翻整个数据层。纠偏目标是恢复清晰职责与可用验证，不是继续围绕个别题目增加规则。
