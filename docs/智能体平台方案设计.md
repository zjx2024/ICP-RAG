# 通用知识库智能体平台技术方案

## 一、技术决策

### 1.1 确定的技术栈

| 层级 | 选型 | 版本 | 决策理由 |
|------|------|------|----------|
| **Agent 引擎** | **LangGraph** | 1.x GA | Python Agent 框架第一（4020 万下载/月），原生 ReAct 状态图 + Checkpoint + 并行 + 流式，LinkedIn/Uber/Klarna/Replit 生产级验证 |
| **后端** | **FastAPI** | 0.115+ | 高性能异步，与你现有知识图谱项目同技术栈，可复用 PG/ES/HG 客户端代码 |
| **前端** | **Vue 3 + Element Plus** | 3.5+ | 配置界面 + 对话界面，生态成熟 |
| **LLM 接入** | **Ollama + OpenAI 兼容 API** | — | 优先 Ollama 本地模型（qwen2.5:14b），同时支持任意 OpenAI 格式 API（DeepSeek/通义/GLM 等），Web 页面切换 |
| **可观测性** | **LangSmith** | — | 全链路追踪 + 调试 + 评估，LangGraph 原生集成 |
| **会话持久化** | **PostgreSQL**（复用现有） | 15 | Agent 配置 + Checkpoint + 对话历史，无需新增组件 |

### 1.2 为什么选 LangGraph 而不是其他

**排除 Claude Agent SDK**：锁定 Anthropic，不支持 Ollama 本地模型，不适合内网部署场景。

**排除 OpenAI Agents SDK**：生态较新（2025 年才发布），生产案例少，与 OpenAI API 绑定较深。

**排除纯自研 ReAct 循环**：需要自己实现 Checkpoint 持久化、并行工具执行、流式输出、错误恢复、状态机路由，工程量大且容易踩坑。Devin/Cursor 走自研路线因为有专职团队（50+ 工程师），不适合个人/小团队。

**排除 CrewAI/Pydantic AI**：CrewAI 适合多 Agent 角色协作场景，但状态管理弱；Pydantic AI 类型安全但生态新、社区小。

**LangGraph 的决定性优势**：

| 能力 | LangGraph 原生支持 | 自研需要的工作量 |
|------|-------------------|-----------------|
| ReAct 循环 | `add_conditional_edges` 天然实现 | 自己写 while 循环 + 状态管理 |
| 工具并行 | 分支节点自动并行 | 自己实现线程池 + 等待逻辑 |
| Checkpoint 持久化 | `PostgresSaver` 开箱即用 | 自己序列化状态 + 存 PG |
| 断点恢复 | `thread_id` 自动恢复 | 自己实现状态恢复 |
| 流式输出 | `astream_events` 原生支持 | 自己接 SSE + token 流 |
| 全链路追踪 | LangSmith 一行集成 | 自己埋点 + 收集 |
| Human-in-the-loop | `interrupt_before` 原生支持 | 自己实现暂停/恢复 |

### 1.3 Agent 策略决策：ReAct + Plan-and-Execute 混合

基于对 Claude Code / Codex / Cursor / Devin 的架构分析，确定采用 **ReAct + Plan-and-Execute 混合策略**：

```
                    ┌─────────────┐
                    │ Plan（规划） │ ← 意图分析 + 任务拆解（Devin 风格）
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
        ┌─────┴─────┐ ┌───┴────┐ ┌─────┴─────┐
        │ ReAct循环1 │ │ReAct2  │ │ ReAct循环3 │ ← 每步独立 ReAct（Claude 风格）
        │ 推理→工具  │ │推理→工具│ │ 推理→工具  │
        │ →观察→循环 │ │→观察   │ │ →观察→循环 │
        └─────┬─────┘ └───┬────┘ └─────┬─────┘
              │            │            │
              └────────────┼────────────┘
                           │
                    ┌──────┴──────┐
                    │ Reflect（反思）│ ← 评估结果充分性，不够则重试
                    └──────┬──────┘
                           │
                    ┌──────┴──────┐
                    │ Answer（回答）│ ← 融合所有结果生成最终答案
                    └─────────────┘
```

**为什么不是纯 ReAct**：纯 ReAct 每步临场决策，容易走偏。加上 Plan 节点先做意图分析和任务拆解（Devin 的核心优势），全局更有方向感。

**为什么不是纯 Plan-and-Execute**：纯 Plan 过于刚性，无法应对检索结果不充分的情况。加上 Reflect 节点做反思评估（Claude Code 的核心优势），可以动态补充检索。

## 四、LangGraph 状态机实现

### 4.1 状态定义

```python
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    # ── 输入 ──
    messages: Annotated[list, operator.add]    # 对话历史（累加）
    query: str                                  # 用户原始问题
    kb_id: str                                  # 知识库ID

    # ── Plan 阶段产出 ──
    intent: str                                 # 识别的意图: document/graph/table/hybrid
    rewritten_query: str                        # 改写后的查询
    entity_keywords: list                       # 提取的实体关键词
    type_keywords: list                         # 提取的类型关键词

    # ── Execute 阶段产出 ──
    vector_results: list                        # ES向量检索结果
    kg_summary: str                             # HugeGraph检索摘要
    sql_results: list                           # PostgreSQL查询结果

    # ── Reflect 阶段产出 ──
    reflection: str                             # 反思内容
    need_more: bool                             # 是否需要补充检索
    next_action: str                            # 下一步动作: retry/document/graph/table/done

    # ── 元信息 ──
    tool_calls: list                            # 工具调用记录（含参数+结果+耗时）
    iteration: int                              # 当前迭代次数（防无限循环）
    final_answer: str                           # 最终答案
```

### 4.2 状态图定义

```python
from langgraph.graph import StateGraph, END

graph = StateGraph(AgentState)

# ═══════════════════════════════════════════
# 节点定义
# ═══════════════════════════════════════════

# ① Plan: 意图分析 + 问题改写 + 关键词提取
graph.add_node("plan", plan_node)
# LLM 分析用户问题，输出: intent, rewritten_query, entity_keywords, type_keywords
# 对标: Devin 的 Planning Module

# ② Execute: 向量检索 (ES)
graph.add_node("vector_search", vector_search_node)
# 调用 ES knn + multi_match，输出: vector_results

# ③ Execute: 知识图谱检索 (HugeGraph)
graph.add_node("kg_search", kg_search_node)
# 复用 dify_code_node_kg_lite.py 逻辑，输出: kg_summary

# ④ Execute: SQL查询 (PostgreSQL)
graph.add_node("sql_query", sql_query_node)
# 查 document_images/document_tables，输出: sql_results

# ⑤ Reflect: 反思评估
graph.add_node("reflect", reflect_node)
# LLM 评估检索结果是否充分，输出: reflection, need_more, next_action
# 对标: Claude Code 的观察+决策

# ⑥ Answer: 生成最终回答
graph.add_node("answer", answer_node)
# LLM 基于所有检索结果生成中文回答，输出: final_answer

# ═══════════════════════════════════════════
# 边定义（流转逻辑）
# ═══════════════════════════════════════════

graph.set_entry_point("plan")

# Plan → Route: 根据意图选择工具（支持并行分支）
graph.add_conditional_edges(
    "plan",
    route_by_intent,
    {
        "document": "vector_search",               # 文档问答 → 只查ES
        "graph": "kg_search",                      # 实体关系 → 只查HG
        "table": "sql_query",                      # 表格数据 → 只查PG
        "hybrid": ["vector_search", "kg_search"],  # 综合诊断 → ES+HG并行
    }
)

# 所有工具执行完 → Reflect
graph.add_edge("vector_search", "reflect")
graph.add_edge("kg_search", "reflect")
graph.add_edge("sql_query", "reflect")

# Reflect → 决策: 补充检索 or 生成答案
graph.add_conditional_edges(
    "reflect",
    decide_next,
    {
        "retry_document": "vector_search",  # 信息不够，补充ES检索
        "retry_graph": "kg_search",         # 信息不够，补充HG检索
        "retry_table": "sql_query",         # 信息不够，补充PG查询
        "done": "answer",                   # 信息充分，生成答案
    }
)

# Answer → 结束
graph.add_edge("answer", END)

# ═══════════════════════════════════════════
# 编译
# ═══════════════════════════════════════════

app = graph.compile(
    checkpointer=PostgresSaver(pg_conn),    # Checkpoint 持久化到 PG
    interrupt_before=["answer"],            # 可选: 生成答案前暂停（human-in-the-loop）
)
```

## 五、工具实现

### 5.1 向量检索工具（ES）

```python
from langchain_core.tools import tool

@tool
def vector_search(query: str, kb_id: str, top_k: int = 5) -> str:
    """在ES向量库中搜索文档块（文本/图片/表格）。

    使用 bge-m3 生成查询向量，ES knn + multi_match 混合检索。
    返回文档内容、图片路径、表格ID。
    """
    # 1. Ollama 生成查询向量
    query_vec = _embed(query)  # 复用现有 _embed() 函数

    # 2. ES 混合检索
    resp = es_client.search(
        index="knowledge_graph_default",
        body={
            "size": top_k,
            "query": {
                "bool": {
                    "must": [{"term": {"kb_id": kb_id}}],
                    "should": [
                        {"knn": {"field": "content_vector",
                                 "query_vector": query_vec,
                                 "k": top_k, "num_candidates": 50}},
                        {"multi_match": {"query": query,
                                         "fields": ["content", "doc_name"]}}
                    ]
                }
            }
        }
    )
    return _format_vector_results(resp)
```

### 5.3 SQL查询工具（PostgreSQL）

```python
@tool
def sql_query(sql: str) -> str:
    """在PostgreSQL中查询图片/表格元数据。

    安全限制: 仅允许SELECT，自动添加 is_deleted = FALSE，默认LIMIT 20。
    """
    sql = sql.strip()

    # 安全检查: 仅允许 SELECT
    if not sql.upper().startswith("SELECT"):
        return "错误: 仅允许SELECT查询"

    # 自动添加 is_deleted 条件
    if "is_deleted" not in sql.lower():
        if "WHERE" in sql.upper():
            sql = sql.replace("WHERE", "WHERE is_deleted = FALSE AND", 1)
        else:
            sql += " WHERE is_deleted = FALSE"

    # 自动添加 LIMIT
    if "LIMIT" not in sql.upper():
        sql += " LIMIT 20"

    rows = pg_client.execute(sql)
    return _format_as_markdown_table(rows)
```

```python
    if agent_config.enable_kg_search:
        tools.append(kg_search)
    if agent_config.enable_sql_query:
        tools.append(sql_query)
    return tools
```

## 六、核心节点实现

### 6.1 Plan 节点

```python
async def plan_node(state: AgentState) -> dict:
    """意图分析 + 问题改写 + 关键词提取。

    对标: Devin 的 Planning Module
    """
    prompt = f"""分析用户问题，提取以下信息:

用户问题: {state["query"]}

请输出JSON:
{{
  "intent": "document|graph|table|hybrid",
  "rewritten_query": "改写后的检索查询",
  "entity_keywords": ["实体1", "实体2"],
  "type_keywords": ["类型1"]
}}

意图判断规则:
- document: 查文档内容、故障现象、标准条款
- graph: 查实体关系、故障原因链、设备间关联
- table: 查表格原始数据
- hybrid: 综合诊断（多种信息需要）
"""
    response = await llm.ainvoke(prompt)
    parsed = parse_json(response)

    return {
        "intent": parsed["intent"],
        "rewritten_query": parsed["rewritten_query"],
        "entity_keywords": parsed["entity_keywords"],
        "type_keywords": parsed["type_keywords"],
        "iteration": state.get("iteration", 0) + 1,
    }
```

### 6.2 Reflect 节点

```python
async def reflect_node(state: AgentState) -> dict:
    """反思评估: 检索结果是否充分？

    对标: Claude Code 的观察+决策循环
    """
    # 防止无限循环
    if state.get("iteration", 0) >= 3:
        return {"need_more": False, "next_action": "done"}

    # 评估检索结果
    has_vector = len(state.get("vector_results", [])) > 0
    has_kg = len(state.get("kg_summary", "")) > 0
    has_sql = len(state.get("sql_results", [])) > 0

    prompt = f"""评估检索结果是否充分回答了用户问题。

用户问题: {state["query"]}
向量检索结果数: {len(state.get("vector_results", []))}
知识图谱摘要长度: {len(state.get("kg_summary", ""))}
SQL结果数: {len(state.get("sql_results", []))}

请判断:
1. 现有信息是否足以回答用户问题?
2. 如果不够，需要补充哪种检索?(document/graph/table/done)
"""
    response = await llm.ainvoke(prompt)
    parsed = parse_json(response)

    return {
        "reflection": parsed.get("reasoning", ""),
        "need_more": parsed.get("need_more", False),
        "next_action": parsed.get("next_action", "done"),
    }
```

### 6.3 Answer 节点

```python
async def answer_node(state: AgentState) -> dict:
    """基于所有检索结果生成最终回答。"""
    context_parts = []

    if state.get("vector_results"):
        context_parts.append(f"【文档检索结果】\n{format_vector(state['vector_results'])}")

    if state.get("kg_summary"):
        context_parts.append(f"【知识图谱检索结果】\n{state['kg_summary']}")

    if state.get("sql_results"):
        context_parts.append(f"【数据库查询结果】\n{format_sql(state['sql_results'])}")

    context = "\n\n".join(context_parts)

    prompt = f"""你是知识图谱助手。基于以下检索结果回答用户问题。

用户问题: {state["query"]}

检索结果:
{context}

请用中文回答，引用检索结果中的具体信息。如果信息不足，如实说明。
"""
    # 流式输出
    final_answer = ""
    async for chunk in llm.astream(prompt):
        final_answer += chunk.content
        yield chunk  # SSE 推送到前端

    return {"final_answer": final_answer}
```

## 十二、关键设计决策总结

| 决策点 | 选择 | 理由 |
|--------|------|------|
| Agent 引擎 | LangGraph 1.x | Python 第一，生产级验证，原生 ReAct + Checkpoint |
| 推理策略 | ReAct + Plan-and-Execute 混合 | Claude Code 的 ReAct + Devin 的 Plan，取长补短 |
| LLM | Ollama 优先 + OpenAI 兼容 API | 内网部署优先，兼容外部模型 |
| 数据源 | 直接访问 PG/ES/HG | 无 sandbox 限制，无 SSRF 代理 |
| 工具数量 | 3 个核心工具 | Cursor 哲学：工具越少越好，每个做到极致 |
| 会话持久化 | PostgreSQL Checkpoint | 复用现有 PG，支持断点恢复 |
| 前端 | Vue3 + Element Plus | 配置界面 + 对话界面，生态成熟 |
| 部署 | Docker Compose | 与现有项目一致，一键启动 |
