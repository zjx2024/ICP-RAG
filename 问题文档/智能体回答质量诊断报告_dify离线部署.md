## 2. 回答"一般"的根因

### 2.1 表层：答案"拼凑感"强、引用张冠李戴

回答虽然步骤完整，但对照文档会发现明显问题：

- 第 3 步"配置环境变量 `cp .env.docker.example .env.docker`"标注的引用 **[^5] 是 ICP fault 章节**（`8_4_启动文件系统核心ICP_fault镜像`），不是 Dify 的步骤；
- 引用 **[^6] 是 ICP 文件系统图片**，与 Dify 部署无关；
- 真正的 Dify 部署核心章节（`h1_012_dify离线部署`，4.1 打包 tar 文件）在召回中排到 **第 14 位** 才进入上下文。

### 2.2 中层：向量召回被无关章节污染

文档是**多子系统总部署手册**（Dify / GPUStack / ICP fault / RAGFlow 多个部署章节共存）。问题被改写为"麒麟V10 离线部署 Docker Compose 文件权限配置指南"后，GPUStack / ICP fault 的章节同样是"离线部署 + Docker + 权限修复"语义，向量相似度极高，一并被召回。

### 2.3 深层：机制缺陷（三层叠加）

1. **retrieval_top_k=25 过大**：该智能体配置了 `retrieval_top_k=25`（默认 5）。跨章节相似内容有大量进入机会，是污染放大的直接原因。
2. **未配置 rerank 模型**：`agent_models` 只绑定了 plan/reflect/answer（qwen3.6）+ embedding（bge-m3），**无 rerank**。若启用 rerank（top_k×3 候选 → 重排序 → top_k），真正相关的 Dify 内容会排到最前，GPUStack/ICP 会被压到后面被截断。
3. **answer 节点硬取前 15 条、无相关性过滤**（[answer.py](file:///home/kdfy/test_code/知识图谱/backend/agent/nodes/answer.py) `_format_context` / `_extract_citations`）：
   - 不区分 chunk 与问题是否相关；
   - 不剔除"图片描述类"chunk（`_img_` 分块内容是解析器生成的图片描述，对文本回答价值低）；
   - 不去重（同一图片/内容的多份索引会全部进入引用）；
   - LLM 被迫在 7/15 的噪音中组织答案 → 拼凑感 + 张冠李戴。

## 3. 解决方案

### 3.1 配置层（最快见效，无需改代码）

| 动作 | 做法 | 预期效果 |
|---|---|---|
| **调小检索条数** | 智能体管理 → 该智能体 → retrieval_top_k 25 → **8~10** | 无关内容进入机会直接减半以上 |
| **配置 rerank 模型** | 在模型管理中新建 rerank 模型（如 bge-reranker，Ollama/TEI 均可）→ 侧边栏绑定该智能体的 Rerank 槽位 | 相关性排序，Dify 核心章节排前、GPUStack 压后（当前最有效手段） |

### 3.2 代码层（质量提升更彻底，建议实施）

1. **answer 上下文过滤**（`_format_context` / `_extract_citations`）：
   - 对 `vec_results` 按内容前 120 字**去重**（同一 chunk 多次索引只保留分数最高一条）；
   - 剔除"图片描述类"chunk（chunk_id 含 `_img_` 或 content 以「图片:」开头）——除非用户明确要求看图；
   - 按 score 截断或只取与问题主题一致的内容。
2. **citation 去重**：相同 chunk_id 只保留一条引用。
3. **prompt 强化**（`ANSWER_PROMPT`）：新增要求——"仅使用与用户问题直接相关的检索结果；无关内容（如其他系统的部署章节、图片描述）一律忽略，不要引用"。

### 3.3 数据层（治本）

- 文档被重复索引产生多份 doc_id 的相同 chunk（306 个分块中包含大量重复，历史解析所致）。清理旧 doc_id 的冗余索引可整体提升召回信噪比（影响所有库，建议统一处理）。

## 4. 验证方法

1. 改动后对同一问题重跑 `POST /api/chat`，对比：
   - vector_search 前 15 条中无关内容占比（目标 < 2/15）；
   - citations 中是否还出现 GPUStack/ICP 引用；
   - [^编号] 与引用原文是否一一对应（不再张冠李戴）。
2. 配置 rerank 后查看 tool_call 事件是否带 `reranked: true`，且 rerank 分数排序是否符合直觉。

---

## 5. 结论

回答"一般"的根因**不是模型不行、也不是文档没内容**，而是：检索条数过大（25）叠加无 rerank，导致答案上下文里混入约一半的无关子系统内容，LLM 在噪音中组织答案，产生拼凑感与错误引用。按 3.1 + 3.2 执行后，回答的相关性与可信度会有可感知的提升。
